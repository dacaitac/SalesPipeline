# Technical Specifications Document: Automated Lead Qualification Orchestrator

## 1. Context and System Objectives
The primary objective is to build an automated orchestration layer for the Addi sales pipeline. This system replaces current manual validations, determining if a lead is qualified to advance to the "Prospect" stage by validating their personal information.

## 2. System Requirements

### Functional Requirements
* **Data Input:** Processing of leads containing a national identification number, birthdate, first name, last name, and email.
* **Validations (Acceptance Criteria):**
    1.  *National Registry:* The individual must exist in the external registry, and their data must match the local database.
    2.  *Judicial Records:* The individual must have no records in the national archives' external system.
    3.  *Compliance Bureau (OFAC):* A lightweight check against a compliance bureau.
    4.  *Qualification Score:* An internal system provides a random score between 0 and 100; a lead is converted only if the score is greater than 60.

### Non-Functional Requirements & Constraints
* **Language:** Java (JVM).
* **Concurrency:** The Registry and Judicial validations must execute in parallel.
* **Sequential Dependency:** The Compliance Bureau requires the successful output of the first two validations. The Qualification Score requires the successful output of the Compliance Bureau.
* **Resilience & Performance:** Implement a persistent/durable caching mechanism for the Compliance Bureau. The system must handle failures gracefully or trigger a manual review flow if the service is down.
* **Infrastructure:** A simple CLI interface. No external databases or message queues are permitted. External systems must be simulated with stubs and artificial latency.

---

## 3. Design and Architectural Decisions (The "Why")

### 3.1. Hexagonal Architecture and Dependency Inversion Principle (DIP)
* **Decision:** Define strict interfaces (Ports) for any infrastructure dependency or external service, implementing the logic in interchangeable Adapters.
* **Why (Database Flexibility):** Since external databases are prohibited, local files will be used via a `ComplianceCacheRepository` interface. By depending on this abstraction, an adapter for an in-memory database (like H2) or a relational engine (like PostgreSQL) can be injected in the future without modifying domain or orchestrator logic.
* **Why (External Client Flexibility):** Currently, registry calls are simulated using functions that return success/failure and inject artificial latency. By isolating these calls behind interfaces, they can be easily swapped for real HTTP clients (e.g., Java 11+ `HttpClient`, Retrofit) in a production environment, keeping the application flow intact.

### 3.2. Immutable Domain Model
* **Decision:** Model the `Lead` entity and validation results using Java `Records`.
* **Why:** Because the first step requires parallel processing, immutable state prevents race conditions and ensures data flows safely between threads without synchronization locks.

### 3.3. Core Design Patterns
* **Strategy:** Each validation implements a common contract. This adheres to the Open/Closed Principle (OCP), allowing new validations to be added without altering existing ones.
* **Orchestrator:** Centralizes coordination. It avoids coupling between services; the judicial check has no logic to trigger the compliance bureau.
* **Decorator:** Wraps the Compliance Bureau call to inject caching and fallback (manual review) capabilities, separating these cross-cutting concerns from pure business rules.

### 3.4. Concurrency Strategy
* **Decision:** Use `CompletableFuture` with a configured `ExecutorService` (Fixed Thread Pool).
* **Why:** Avoids using the default global pool. It defines structured asynchrony to meet parallelism  and sequential dependencies. Explicit timeouts (`orTimeout`) are included to ensure the CLI does not block indefinitely due to extreme latency in the simulated stubs.

## 4. Observability and Logging

* **Decision:** Implement a structured logging system (e.g., SLF4J with Logback).
* **Why:** Essential in concurrent systems to trace the lifecycle of a request.
* **Implementation:**
    * **Traceability:** Use MDC (Mapped Diagnostic Context) to inject the lead's national ID into all logs generated by different threads. This unifies the trace of a single lead across parallel processing.
    * **Levels:** Use `INFO` for the start and end of key stages, `WARN` for degradation events (e.g., cache miss or OFAC service failure triggering manual review), and `ERROR` for fatal pipeline failures.

---

## 5. Testing Strategy

A multi-layered testing approach will be adopted to ensure the correct functioning and interchangeability of components:

* **Unit Testing:**
    * **Goal:** Validate business logic, orchestrator flow, and design patterns in total isolation.
    * **Tools:** JUnit 5 and Mockito.
    * **Scenarios:** Mock client and repository interfaces. Validate that the orchestrator respects parallelism (Step 1) and sequentiality (Steps 2 and 3). Exhaustively test the Decorator to ensure it catches exceptions and correctly returns the manual review state.
* **Integration Testing:**
    * **Goal:** Verify that concrete adapters interact correctly with their infrastructure environment.
    * **Scenarios:** Validate that the file-based cache implementation successfully persists and retrieves data from disk. These tests lay the groundwork so that when switching to H2 or real HTTP clients, connectivity and data mapping can be verified (e.g., using tools like WireMock for HTTP clients).
